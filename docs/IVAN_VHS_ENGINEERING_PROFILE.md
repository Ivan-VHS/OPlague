# OPlague — профиль безопасной диагностики устройств и драйверов

**Проект:** Ivan-VHS/OPlague  
**Автор инженерного направления:** Ivan-VHS  
**Статус документа:** контракт безопасного развития и критерии проверки.

## Назначение

OPlague — локальная рабочая станция для read-only инвентаризации Windows Plug and Play, анализа метаданных пакетов драйверов и сопоставления аппаратных идентификаторов с доказательствами. Пользователь должен понимать не только результат, но и происхождение каждого факта.

## Правила доказательной диагностики

1. **Наблюдаемое отделено от предполагаемого.** Сведения Windows, поля INF, заголовки PE/COFF, подпись, hash и вывод алгоритма хранятся раздельно.
2. **У каждого утверждения есть происхождение.** Указывать источник, путь, время получения, версию парсера и точное поле, из которого получен вывод.
3. **Совпадение не является вердиктом.** Совпавший hardware ID не доказывает безопасность, издателя, совместимость со сборкой Windows или корректность установки.
4. **Пакет недоверенный до проверки.** Пути, размеры, compression ratio, количество записей, вложенность и целостность проверяются до чтения содержимого.
5. **Инспекция остаётся read-only.** Не выполнять INF directives, не запускать payload, не загружать драйверы и не устанавливать пакеты.
6. **Неопределённость видима.** Отсутствующая подпись, неизвестный идентификатор и частично разобранный файл обозначаются явно, а не превращаются в «успех».

## Модель доказательств

Каждая запись должна позволять восстановить цепочку:

`input → parser/version → extracted fact → normalization → comparison → explanation`

Рекомендуемые типы:

- **Observed:** получено непосредственно из ОС или файла.
- **Parsed:** извлечено безопасным парсером из определённой структуры.
- **Normalized:** приведено к канонической форме без потери оригинала.
- **Matched:** сопоставлено по точному или явно указанному правилу.
- **Inferred:** аналитическое предположение с объяснением.
- **Unresolved:** недостаточно данных для вывода.

У каждого нормализованного значения сохраняется исходное. Правило сопоставления должно быть названо; fuzzy-match никогда не маскируется под exact-match.

## Безопасная обработка файлов

- Проверять абсолютные и traversal-пути, имена с разделителями, дубли и Unicode edge cases.
- До распаковки/чтения учитывать общий объём, размер записи, количество файлов, compression ratio и глубину.
- Не извлекать исполняемые payload-файлы в рабочую среду для запуска.
- Для PE/COFF проверять границы DOS/PE заголовков, таблиц секций, optional header и смещений до каждого чтения.
- Для Authenticode отличать наличие структуры подписи, криптографическую проверку и доверие к цепочке сертификатов.
- Любой лимит — централизованная константа/политика с тестом граничного значения.

## Сквозной сценарий

1. Пользователь выбирает источник: PnP snapshot или локальный пакет.
2. Приложение создаёт неизменяемую запись о входе и его hash.
3. Парсер выполняет ограниченное чтение и формирует извлечённые факты.
4. Нормализатор сохраняет пару original/canonical.
5. Граф совместимости строит кандидатов по объяснимым правилам.
6. Отчёт перечисляет совпадения, расхождения, неизвестные данные и ограничения.
7. Экспорт создаётся атомарно, с версией схемы и provenance.

## Критерии приёмки

| Область | Что проверяется |
|---|---|
| PnP | недоступный источник, пустой snapshot, отсутствующие поля |
| INF | неизвестные директивы остаются данными, не исполняются |
| ZIP | traversal, zip bomb, дубли, неверные CRC, чрезмерные размеры |
| PE/COFF | усечённые заголовки, overflow смещений, неверная таблица секций |
| Идентификаторы | case, разделители, hardware ID vs compatible ID, сохранение исходной строки |
| Подпись | различие между подписью, валидностью и доверенной цепочкой |
| Отчёт | provenance каждого заключения, версия схемы, атомарная запись |
| Безопасность | тесты доказывают отсутствие запуска/установки/изменения драйвера |

## Человеческий интерфейс

Тон сообщений — спокойный и инженерный. Вместо «драйвер безопасен» писать «подпись проверена», «идентификатор совпал» или «данных недостаточно». Ошибка должна показывать, какой элемент не удалось прочитать и можно ли продолжить анализ других элементов.

## Управление объёмом

Новые панели, каталоги и рейтинги добавляются только тогда, когда улучшают сквозной сценарий проверки. Сначала — надёжное доказательство и ясный отчёт; затем — удобство сравнения; после — автоматизация. Это сохраняет мощь инструмента без превращения количества функций в замену проверяемости.

**Итоговая формула OPlague:** не доверяй входу → сохрани происхождение → проверь границы → объясни совпадение → не выполняй payload.
