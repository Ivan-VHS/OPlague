# Driver Vault, Clean-Extract и жизненный цикл драйвера

## 1. Каталог пакетов

Driver Vault хранит неизменённый оригинальный пакет и отдельную запись происхождения: источник, URL/путь импорта, дата получения, SHA-256, поставщик, версия, класс, Hardware IDs, Compatible IDs, целевые ОС, зависимости и состояние подписи.

Имя файла не является доказательством поставщика или версии. Источником версии являются метаданные пакета и/или доверенный API ОС; противоречия фиксируются.

## 2. Clean-Extract pipeline

1. Создать временный каталог с ограниченными правами.
2. Проверить тип, размер, число файлов и вложенность архивов.
3. Распаковать только поддерживаемые форматы без запуска скриптов/installer payload.
4. Разобрать INF как декларативный текст с ограничениями парсера.
5. Найти ссылки на SYS/CAT/DLL и установить их принадлежность.
6. Построить dependency manifest.
7. Проверить hash и подписи оригинальных артефактов.
8. Сформировать отчёт с состояниями «обнаружено / неизвестно / подтверждено».
9. Сохранить оригинал неизменным.
10. Подготовить новый пакет только как отдельный артефакт.

EXE — исполняемый файл. По умолчанию он не запускается. Если поддерживается документированный vendor extraction switch, он применяется только в изолированной среде и с видимым согласием пользователя. Иначе пакет помечается «требуется внешний безопасный источник/ручная распаковка».

## 3. Цифровые подписи

- Проверять подпись средствами доверенной ОС/каталога сертификатов.
- Записывать сертификат подписанта, цепочку, timestamp и результат проверки.
- Проверять, что CAT покрывает файлы пакета.
- Любое изменение подписанного пакета аннулирует исходное доказательство целостности.
- Локальный self-signed certificate не приравнивается к Microsoft WHQL или доверенной подписи производителя.
- Не отключать enforcement ради установки неподписанного пакета.

## 4. Совместимость

Совместимость оценивается по ОС/build/архитектуре, Hardware ID/Compatible ID, классу, зависимостям, подписи и известным ограничениям. Статус кандидата: Compatible, PotentiallyCompatible, Conflict, Unsupported или Unknown. Unknown не превращается в Compatible.

## 5. Установка и удаление

Любая write операция обязана иметь:
- точное устройство и пакет;
- diff ожидаемых изменений;
- проверку платформы и подписи;
- проверку зависимостей;
- проверенный baseline/snapshot;
- подтверждение пользователя;
- запуск через allowlisted OS API/service;
- post-install validation;
- журнал результата;
- план отката.

Операции запрещаются, если не удаётся получить необходимый snapshot, проверить целевой пакет или установить безопасное состояние для восстановления.

В Windows механизм должен опираться на SetupAPI/Configuration Manager и документированные операции Driver Store. Нельзя самостоятельно удалять случайные файлы из DriverStore или чистить нераспознанные registry keys.

## 6. Сиротские устройства и пакеты

Понятия «дублирующийся», «старый» и «неиспользуемый» требуют доказательства. Не удалять устройства из-за совпадения friendly name. Сравнивать instance IDs, parent/child relationship, hardware IDs, provider и package bindings. Сначала показывать preview и предлагать экспорт/backup.

## 7. Driver Lifecycle состояния

Discovered → CandidateFound → PackageVerified → CompatibilityChecked → PlanPrepared → SnapshotVerified → AwaitingConfirmation → Applying → Verifying → Completed.

При отказе: Rejected, Failed, RollbackRequired, RolledBack или ManualRecoveryRequired. Все переходы сопровождаются структурированным событием.
