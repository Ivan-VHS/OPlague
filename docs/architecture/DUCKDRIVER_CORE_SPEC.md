# OPlague — DuckDriver Core (DDC)
## Функциональная и архитектурная спецификация нативного десктопного приложения

**Версия:** 0.1.0  
**Статус:** архитектурная основа продукта; функции ниже являются проектными требованиями, а не заявлением об уже реализованной функциональности.  
**Рабочее имя продукта:** DuckDriver Core (DDC).  
**Назначение репозитория:** OPlague.  
**Приоритетная платформа первого выпуска:** Windows 11 x64.  
**Архитектурная цель:** нативное ядро на Rust, отдельная привилегированная служба и нативный графический интерфейс без Electron и WebView2.

## 1. Продуктовая интерпретация исходного документа

OPlague должен стать локальным центром инвентаризации, диагностики, безопасного управления и согласования драйверов и аппаратных подсистем. Это не «обновлятор всех драйверов» и не оболочка для запуска сторонних установщиков. Продукт собирает фактическую картину оборудования, понимает отношения между устройствами и их драйверами, объясняет проблемы, предлагает безопасные изменения и сохраняет возможность возврата.

Основная ценность DDC:

1. Единая карта устройств, шин, контроллеров, зависимостей и активных драйверов.
2. Контролируемый жизненный цикл драйверов: обнаружение, проверка происхождения, подготовка, установка, проверка результата и откат.
3. Унифицированная модель возможностей периферии через адаптеры UDB, а не обещание универсального управления любым устройством.
4. Измеряемая диагностика задержек, событий Plug and Play и конфликтов ресурсов.
5. Профили конфигурации для разных режимов использования с предварительным просмотром изменений.
6. Нативный интерфейс с ясной иерархией и минимальным количеством действий до важной функции.

### 1.1. Что именно берётся из разных частей документа

Их применимые инженерные идеи — типобезопасность, явные эффекты, композиция, неизменяемость конфигурации, проверяемые контракты и изоляция — используются в реализации DDC, но сам язык в OPlague не разрабатывается.

## 2. Цели, границы и инварианты продукта

### 2.1. Цели

- Получать полную, насколько позволяют API платформы, картину устройств и активных драйверов.
- Показывать связи «устройство — контроллер — шина — драйвер — зависимость».
- Находить конфликты, деградацию режима работы и потенциальные узкие места.
- Объяснять причину рекомендации и ожидаемый эффект.
- Работать с официальными и проверяемыми пакетами драйверов.
- Давать возможность подготовить изменение, предварительно увидеть его последствия и выполнить его с повышенными правами только после подтверждения пользователя.
- Сохранять исходное состояние и обеспечивать проверяемый откат.
- Постепенно объединять управление совместимой периферией в единый слой UDB.
- Оставаться полезным в режиме только чтения, без установки собственного драйвера ядра.

### 2.2. Не-цели и запрещённые обещания

- Не обещать, что произвольный драйвер можно запустить в универсальном контейнере или безопасно переключить без перезагрузки.
- Не перехватывать по умолчанию системный PnP-процесс и не блокировать штатную установку драйвера операционной системой.
- Не изменять подписанные файлы драйвера и не заявлять, что после изменения сохранилась исходная WHQL-подпись.
- Не устанавливать корневые сертификаты DDC для обхода политики доверия ОС.
- Не устанавливать неподписанные драйверы, не отключать Secure Boot, проверку подписи или защитные механизмы ОС ради «унификации».
- Не менять IRQ, MSI/MSI-X, affinity, параметры питания, реестр и службы автоматически без анализа, предварительного просмотра, согласия и плана отката.
- Не обещать нулевую дополнительную задержку для любой аудиомаршрутизации или поддержку всех производителей и моделей.
- Не собирать аппаратные серийные номера, имена пользователей и сырые системные дампы для DuckMesh.
- Не показывать демонстрационные или синтетические показатели как живую телеметрию реального компьютера.

### 2.3. Неизменяемые инварианты безопасности

1. **Read-only по умолчанию.** Первое сканирование не меняет состояние системы.
2. **Минимальные привилегии.** UI работает без административных прав; привилегированная служба получает только конкретные разрешённые операции.
3. **Явное согласие.** Каждая системная модификация имеет описание, причину, область воздействия и подтверждение.
4. **Проверяемое происхождение.** Пакет имеет источник, хэш, версию, целевое оборудование и результат проверки подписи.
5. **Транзакционность.** До изменения создаётся контрольное состояние; частичный сбой не должен маскироваться под успех.
6. **Восстановимость.** Для каждого обратимого действия определена процедура возврата; необратимые действия маркируются заранее.
7. **Наблюдаемость.** Каждая операция пишет структурированный журнал с идентификатором операции, результатом и кодом ошибки.
8. **Изоляция.** Парсеры пакетов и недоверенных файлов работают с лимитами ресурсов и без привилегий.
9. **Fail-safe.** При неизвестном состоянии приложение прекращает опасную операцию и показывает причину.
10. **Никаких скрытых обходов.** Нельзя обходить политику подписи, права пользователя, системные предупреждения и защиту платформы.

## 3. Архитектура: четыре изолированных слоя

### Слой 1. Platform Access и системные адаптеры

Отвечает за чтение состояния ОС и выполнение строго ограниченного списка поддерживаемых действий. Платформенные API находятся только в адаптерах, а не в UI и не в доменной логике.

**Windows:** SetupAPI, Configuration Manager API (CfgMgr32), WMI/CIM для подходящих классов данных, PnP/ETW для событий и диагностики, штатные механизмы Driver Store и установщика устройств. Низкоуровневые возможности включаются только при наличии документированного API и соответствующих прав.

**Linux:** libudev, sysfs, ioctl и netlink по необходимости; управление модулями и правилами udev через платформенный адаптер; аудиособытия и маршруты — через PipeWire. Доступ к perf/eBPF и расширенным tracepoint требует отдельной проверки прав и конфигурации.

**macOS:** IOKit и публичные системные интерфейсы для инвентаризации. Управление драйверами ограничивается моделью DriverKit/System Extensions, доступными entitlement и согласием пользователя. Нельзя проектировать кроссплатформенный Ring-0-модуль как обязательную часть приложения.

Платформенный контракт возвращает нормализованные наблюдения и возможности. Если платформа не поддерживает действие, UI показывает «не поддерживается», а не имитирует успешное выполнение.

### Слой 2. Hardware Introspection и Telemetry

Модули:

- **Bus Scanner:** PCI/PCIe, USB, ACPI и доступные платформенные шины.
- **Device Inventory:** стабильный идентификатор, класс, производитель, модель, аппаратные ID, ревизия, состояние PnP, родительский контроллер и признаки виртуального устройства.
- **Driver Inspector:** активный драйвер, INF/пакет, поставщик, версия, дата, подпись, связанные файлы и сервисы, насколько их раскрывает ОС.
- **Resource Inspector:** доступные сведения о прерываниях, режимах MSI/MSI-X, диапазонах ресурсов и энергосостояниях.
- **Performance Telemetry:** DPC/ISR, события устройства, задержки и доступные метрики нагрузки.
- **Package Analyzer:** безопасный разбор метаданных INF/CAT/SYS/DLL/KO и архивов без запуска установщика.

Все наблюдения снабжаются источником, временем, уровнем достоверности и признаком «измерено / получено из API / вычислено / предположено». Граф и рекомендации не должны выдавать предположение за факт.

### Слой 3. Orchestration и Unified Driver Bus

Центральная предметная логика. Она не должна содержать прямых вызовов Win32, sysfs или графических API.

**UDB (Unified Driver Bus)** — открытая внутренняя модель возможностей для совместимого оборудования. UDB объединяет функции по типам устройств и адаптерам:

- HID: мыши, клавиатуры, геймпады и контроллеры.
- Параметры ввода: DPI, polling rate, кривые отклика, профили кнопок и макросы — только на поддерживаемых устройствах.
- RGB: обнаружение зон, безопасное чтение возможностей, пресеты и синхронизация.
- Cooling: датчики и кривые вентиляторов через поддерживаемые контроллеры.
- Audio: перечисление endpoint, выбор маршрута, параметры доступного буфера и интеграции с платформенными аудиосистемами.
- On-board profiles: запись в аппаратную память, только если протокол и операция подтверждены для конкретной модели.

Каждый адаптер объявляет производителя, семейство устройств, версии протокола, capabilities, ограничения, необходимые права и поддерживаемые операции. Неизвестное устройство остаётся видимым в инвентаре, но не получает вымышленных настроек.

**Dependency Resolver** строит зависимости пакетов, устройств и компонентов. **Conflict Analyzer** объединяет обнаруженные конфликты и телеметрию, оценивает риск и формирует объяснимые рекомендации. **Snapshot Manager** сохраняет и восстанавливает поддерживаемое состояние. **Profile Manager** рассчитывает дифф конфигураций и исполняет его как последовательность проверяемых операций.

### Слой 4. Native UI (Tri-Color Duck UI)

UI показывает состояние, объясняет причину и передаёт команды сервису через IPC. Он не получает произвольный доступ к реестру, драйверному хранилищу и системным вызовам.

Рекомендуемая связка первого прототипа: Rust + Slint для нативного UI; wgpu подключается для аппаратно-ускоренного графа и специализированных визуализаций только там, где обычных компонентов недостаточно. Это сохраняет один основной язык и отделяет тяжёлые визуализации от бизнес-логики.

## 4. Состав функциональных подсистем

### 4.1. Hardware Inventory

- Первичное сканирование и повторное сканирование оборудования.
- Обнаружение подключения и отключения устройств.
- Группировка по классам: chipset, PCIe, USB, ACPI, GPU, display, audio, storage, network, HID, sensors и virtual devices.
- Просмотр Hardware IDs, VID/PID, VEN/DEV, ревизий, версий прошивки там, где ОС предоставляет эти сведения.
- Сопоставление устройства с активным пакетом драйвера и родительской цепочкой.
- Экспорт отчёта в JSON и человекочитаемый формат.
- История изменения инвентаря с отметкой времени.

### 4.2. Semantic Hardware Graph

Граф является основной моделью навигации по железу, а не декоративной схемой.

**Типы узлов:** CPU, Root Complex, PCIe bridge, PCIe endpoint, USB host controller, hub, HID, GPU, audio endpoint, storage controller, NIC, ACPI device, driver package, virtual UDB device.

**Типы связей:** physical-parent, bus-child, controls, driver-bound-to, depends-on, shares-resource-with, virtualized-by, observed-event.

**Возможности интерфейса:** перемещение по полотну, zoom, фильтры по шине/классу/состоянию, поиск, выделение пути, панель Inspector, сравнение двух состояний и подсветка конфликтов.

Толщина или стиль линии может отражать скорость/тип связи только при наличии достоверного значения. Цвета отражают состояние: штатное, виртуальное, предупреждение, конфликт. У каждого красного узла есть текстовая причина и ссылка на доказательство.

### 4.3. Driver Vault

Локальный каталог проверенных пакетов:

- импорт из официального каталога, локального файла или официального URL;
- хранение исходного пакета без модификации;
- вычисление SHA-256 и фиксация provenance;
- чтение INF, CAT, версий и совместимых Hardware IDs;
- проверка подписи и цепочки доверия средствами платформы;
- выявление дублирующихся, устаревших и несовместимых версий;
- сравнение установленной и предлагаемой версии;
- карантин сомнительных файлов и ограничение запуска парсеров;
- установка, обновление, удаление и откат через поддерживаемый системный механизм;
- журнал действий и экспорт диагностического отчёта.

Нельзя считать любой пакет безопасным лишь потому, что он находится в каталоге. Валидность подписи, доверие издателю, совместимость с устройством и происхождение должны показываться отдельно.

### 4.4. Clean-Extract — безопасная интерпретация

Clean-Extract сохраняется как концепция анализа и подготовки «чистой установки», но не как произвольная пересборка ядрового драйвера.

Допустимая реализация:

1. Распаковать загруженный установочный контейнер в ограниченную временную область без запуска его кода.
2. Просканировать структуру, INF, CAT, модули и дополнительные компоненты.
3. Разделить основной подписанный пакет драйвера и необязательные приложения/службы, если такое разделение подтверждено структурой пакета и документацией производителя.
4. Показать, какие компоненты обязательны, необязательны, неизвестны или потенциально нежелательны.
5. Сформировать план установки из неизменённых исходных пакетов и отдельно предложить отказаться от необязательного companion software только там, где это безопасно.
6. До установки показать исходный размер, выбранные компоненты, подписи, хэши и последствия.

**Критическое ограничение подписи:** если изменить INF, CAT, SYS, DLL или любой файл, покрываемый каталогом подписи, исходная подпись пакета перестаёт подтверждать целостность такого пакета. Поэтому DDC не должен обещать сохранение WHQL после хирургического изменения пакета. Локальный сертификат DDC не является заменой публичной подписи производителя или Microsoft и не должен использоваться для обхода системной политики доверия.

### 4.5. Time Duck — профили и снэпшоты

Time Duck хранит не полный образ ОС, а ограниченное, явно описанное состояние, которым приложение умеет безопасно управлять:

- список текущих пакетов драйверов и соответствие «устройство — пакет»;
- исходные пакеты и их криптографические хэши;
- поддерживаемые параметры устройств;
- настройки UDB;
- параметры профиля, созданные самим DDC;
- перечень системных изменений, которые планируется выполнить и которые реально можно вернуть.

Снэпшот имеет manifest, версию формата, время, платформу, список компонентов, хэши и статус пригодности к восстановлению. Создание и восстановление атомарны настолько, насколько это поддерживают API ОС; после сбоя незавершённая транзакция обнаруживается и помечается.

**Базовые профили:**

- **Balanced / Everyday:** безопасные системные значения по умолчанию.
- **Gaming / Low Latency:** рекомендации по периферии, графике и задержкам; применение — только по устройствам и настройкам с подтверждённой поддержкой.
- **Studio / DAW:** приоритет рабочему аудиоустройству, прозрачная информация о маршрутах и буферах, предотвращение конфликтующих автоматических изменений.
- **Mobile / Power Saving:** энергосбережение и отключение неиспользуемых функций только при поддержке платформы и устройства.
- **Custom:** пользовательский профиль с именем, описанием, изменениями и историей.

Перед применением показывается diff: «было → станет», риск, перезапуск, зависимые устройства и способ отката. Hot-switch без перезагрузки доступен только для конкретной операции, если это официально поддерживается системой и устройством. Необходимость перезапуска показывается до подтверждения.

### 4.6. Latency Lab

- Сбор временных характеристик ISR/DPC и событий драйверов на платформах, где доступен надёжный источник.
- Временная шкала, график, waterfall, пики, percentiles и история сессии.
- Привязка события к модулю/драйверу, если стек и ОС дают такую атрибуцию.
- Поиск пиков, повторяемости и корреляции с фризами, треском звука и изменениями устройств.
- Сравнение «до / после» применения профиля.
- Экспорт отчёта для диагностики.
- Фоновый режим с ограничением частоты сбора и ресурсного бюджета.

Пороговые диапазоны из исходной концепции (менее 250 µs, 250–500 µs, более 500 µs) — начальные визуальные ориентиры, а не универсальный норматив. Порог должен быть настраиваемым, а вывод — учитывать тип нагрузки, длительность пика и метод измерения.

**Affinity Auto-Tune** сначала работает как анализатор и генератор рекомендаций. Автоматическое изменение affinity/привязки прерываний допускается только после измерения baseline, проверки поддержки, подтверждения пользователя и подготовки отката. Нельзя безусловно исключать Core 0 или распределять все прерывания по одной фиксированной схеме.

### 4.7. UDB Hub

Единый экран управления совместимыми устройствами:

- вкладки All, Mouse & Keyboard, Controllers, Audio, Cooling, RGB;
- список физических и виртуальных устройств;
- карта доступных capabilities и активного адаптера;
- настройки DPI/polling/кривых отклика и профилей ввода;
- RGB-сцены и пресеты, включая Duck Classic;
- телеметрия температур, оборотов и питания там, где доступна;
- запись профиля в onboard flash для поддерживаемых моделей;
- диагностика конфликтующих vendor-служб.

DDC не должен принудительно останавливать или блокировать фирменное ПО производителя. Он показывает возможное дублирование функций и предлагает пользователю отключить конкретный компонент только после проверки его назначения и зависимостей.

### 4.8. Duck-Agent и диагностика

Duck-Agent — визуальный и сценарный помощник, а не автономный root-агент.

- **Surface Mode:** спокойное состояние; анимация отражает агрегированную телеметрию без отвлечения пользователя.
- **Kernel Dive:** экспертный режим с деревом шин, сырыми идентификаторами, трассами, источниками событий и расширенными метаданными.
- **Rubber Duck Diagnostics:** пошаговый мастер, который спрашивает, что произошло, собирает согласованные диагностические данные, связывает временную шкалу с устройствами и выделяет вероятный проблемный узел.
- **BSOD Analysis:** импорт и анализ пользовательского minidump без самостоятельной отправки файла в сеть. Сырые дампы могут содержать чувствительные данные.
- **Guided Fix:** список возможных причин, подтверждающие данные, риск и инструкция. Исправление не запускается без отдельного действия пользователя.

### 4.9. DuckMesh Telemetry

DuckMesh — необязательная база совместимости и агрегированных результатов конфигураций.

- Выключена по умолчанию.
- Отдельное информированное согласие до первой отправки.
- Пользователь может посмотреть состав данных, приостановить и отозвать согласие.
- Не отправлять серийные номера, имена пользователей, пути файлов, дампы памяти и необработанные логи.
- Отпечаток конфигурации формируется из минимального набора категорий/моделей и защищённых хэшей; хэш оборудования не считается автоматически анонимным.
- Принимать и показывать только агрегаты с количеством наблюдений и временным окном.
- Любой совет о драйвере содержит версию, платформу, выборку, доверительный уровень и дату.
- Не блокировать установку на основании одного удалённого сигнала.

### 4.10. Dashboard и здоровье системы

Главная панель объединяет:

- общий индекс здоровья;
- карту состояния ключевых подсистем;
- найденные конфликты и деградации;
- список рекомендованных действий;
- ленту живых событий;
- текущий профиль и статус фонового наблюдения.

«Утиный индекс здоровья» рассчитывается по документированным правилам, имеет объяснение каждого снижающего фактора и не подменяет диагностику произвольным процентом. В демонстрационном режиме данные явно помечаются как примеры.

### 5.3. Основные пользовательские сценарии

**Первый запуск**
1. Проверка платформы и статуса службы.
2. Read-only инвентаризация.
3. Построение графа и обнаружение драйверов.
4. Создание Factory Baseline.
5. Отображение фактов, предупреждений и рекомендаций.
6. Каждое исправление применяется отдельно или как явно показанная транзакция.

**Подключение нового устройства**
1. Событие PnP фиксируется системным адаптером.
2. DDC обновляет инвентарь и граф.
3. Подбирает совместимые пакеты по Hardware IDs и доверенному источнику.
4. Показывает capabilities UDB, если есть адаптер.
5. Предлагает безопасный следующий шаг; не подменяет драйвер самовольно.

**Проблемы с микрофризами или звуком**
1. Пользователь запускает сессию Latency Lab.
2. Включается ограниченное фоновое наблюдение.
3. После проблемы пользователь отмечает временной интервал.
4. DDC связывает пики с доступными событиями и модулями.
5. Пользователь получает отчёт, сравнение и безопасные варианты действий.

**Установка или откат**
1. Выбор исходного пакета и целевого устройства.
2. Проверка происхождения, подписи, совместимости и конфликтов.
3. Сохранение baseline/snapshot.
4. Просмотр полного плана изменений и необходимости reboot.
5. Подтверждение и повышение привилегий.
6. Установка штатным системным механизмом.
7. Повторное сканирование и проверка результата.
8. При ошибке — остановка цепочки и предложенный rollback.

**Смена профиля**
1. Выбор профиля.
2. Расчёт diff относительно текущего состояния.
3. Показ неподдерживаемых, требующих перезапуска и потенциально рискованных операций.
4. Создание снэпшота.
5. Применение последовательности операций.
6. Проверка состояния и сохранение результата.

## 7. Технологический фундамент

### 7.1. Предлагаемый стек

- **Язык:** Rust, Edition 2024.
- **UI:** Slint; wgpu для графа/водопада по мере необходимости.
- **IPC:** FlatBuffers поверх Named Pipes на Windows и Unix Domain Sockets на Unix-платформах.
- **Хранилище метаданных:** SQLite в WAL-режиме.
- **Хранение оригинальных пакетов:** content-addressed store по SHA-256; сжатие Zstandard допускается только для собственного архива, не для изменения исходного пакета.
- **Логи:** структурированные JSON/SQLite с ротацией и redaction.
- **CLI:** вспомогательная поверхность для диагностики, автоматизации и тестов; пользовательские опасные операции требуют тех же разрешений, что и GUI.
- **Обновления:** подписанные релизные артефакты, проверка целостности, staged rollout и возможность отката приложения.

### 7.3. IPC-контракт

IPC разделяет команды, события и запросы состояния:

- Command: запрос на действие, обязательно с operation_id и ожидаемым состоянием.
- Event: системное событие или прогресс операции.
- Query: read-only получение инвентаря, графа, драйвера или профиля.
- Result: успешное завершение, контролируемая ошибка либо частичный результат с явным статусом.

Каждое сообщение имеет schema version, ограничение размера, тайм-аут, проверку полномочий и корреляционный ID. Неизвестные версии и поля обрабатываются безопасно. UI не может вызвать произвольную команду ОС через строку.

### 7.4. Служба и запуск

- Служба устанавливается отдельно и запускается с минимальными правами, достаточными для поддерживаемых операций.
- UI стартует без повышения прав и подключается к службе локально.
- Для операции, требующей elevation, используется штатный механизм подтверждения ОС.
- Автозапуск приложения и запуск фоновой службы — разные настройки.
- Автозапуск UI/трей отключён или предлагается пользователю явно; служба не должна запускать интерфейс в интерактивной сессии.
- Сбой UI не должен оставлять незавершённую опасную транзакцию без журнала и процедуры восстановления.

| Платформа | Приоритет | Объём первого этапа |

Портируемость обеспечивается интерфейсами, а не обещанием одинакового набора функций на любой ОС. В UI всегда видны платформенные ограничения.

### 8.1. Опциональный ddc_bridge

Модуль ядра не входит в MVP и не нужен для базовой полезности приложения. Сначала используются ETW/PnP и документированные интерфейсы user mode.

Разработка ddc_bridge.sys или Linux kernel module возможна только при доказанной необходимости, когда пользовательский API не позволяет получить критически важные данные. До включения такого компонента обязательны:

- отдельный документ угроз и модель отказов;
- ограниченный набор функций без произвольного перехвата;
- code review и независимый аудит;
- тесты на целевых версиях ОС и оборудовании;
- подпись и распространение по правилам платформы;
- проверяемое удаление, отключение и восстановление;
- отдельное согласие пользователя и понятный установщик;
- безопасный режим, если модуль не загружается или несовместим.

Целевой размер менее 45 KB и измерение ISR/DPC с точностью 100 ns из исходной концепции — гипотезы для прототипа, а не гарантии продукта.

## 9. Приватность, безопасность и эксплуатация

- Инвентаризация локальна по умолчанию.
- Сетевое соединение требуется только для явно выбранного каталога обновлений, проверки репутации/подписей и опционального DuckMesh.
- Системные дампы, логи и данные устройств не отправляются без отдельного согласия.
- Парсеры ограничивают глубину архивов, число файлов, объём распаковки, время обработки и потребление памяти.
- Архивы проверяются на path traversal, symlink escape, decompression bombs и дублирующие пути.
- Пакеты никогда не исполняются для извлечения метаданных.
- Данные SQLite и snapshot-манифесты валидируются при чтении; файлы контентного хранилища сверяются с SHA-256.
- IPC требует аутентификации локального клиента и авторизации каждой привилегированной команды.
- Секреты не помещаются в логи, события и отчёты.
- Unsafe Rust локализуется в платформенных модулях и снабжается обоснованием инвариантов.
- Все операции установки и изменения имеют аудит, результат и ссылку на snapshot.

## 10. Тестирование и критерии готовности

### 10.1. Слои тестов

1. Unit tests для доменных правил, графа, разрешения зависимостей, профилей и вычисления diff.
2. Property-based tests для идентификаторов, графов, сериализации, парсеров INF/CAT и manifest.
3. Fuzzing для внешних архивов, INF, метаданных устройств и IPC.
4. Integration tests с фиктивными platform adapters.
5. Hardware-in-the-loop тесты на ограниченном каталоге реальных устройств.
6. Compatibility tests для поддерживаемых ОС, архитектур, производителей и версий драйверов.
7. UI tests для навигации, доступности, клавиатуры, масштабирования DPI и состояний ошибок.
8. Recovery tests для аварийного завершения в середине операции и восстановления после перезагрузки.
9. Performance tests для сканирования, IPC, графа, фонового режима и потребления памяти.

### 10.2. Матрица взаимодействия функций

Идея «каждую функцию к каждой» трактуется как проверка реальных связей, а не бесконечное полное перемножение:

- реестр возможностей перечисляет входы, выходы, права, события и зависимости каждого модуля;
- граф интеграций фиксирует поддерживаемые связи между модулями;
- каждая новая функция добавляет тесты для всех затронутых связей;
- критические пары проверяются на совместимость и откат;
- для большой матрицы применяется pairwise и risk-based testing, а для опасных операций — целевые сценарии полного пути.

### 10.3. Release gates

Публикация блокируется, если не проходят форматирование, lint, unit/integration tests, security checks, сборки целевых платформ или проверка подписанных артефактов. Ошибки не устраняются бесконечным повтором одного и того же шага.

Автоматическое слияние допустимо лишь при выполнении настроенных branch rules, обязательных CI-проверок и требуемого человеческого одобрения. Запрещены обход защиты ветки, фиктивные статусы и force-push ради зелёного результата. Документация генерируется или обновляется из фактической схемы, тестов и реализованных возможностей; незавершённые функции помечаются как planned.

## 13. Критерии MVP

MVP считается готовым, когда:

- нативное приложение и локальная служба запускаются на поддерживаемой Windows 11 x64;
- UI не требует административного запуска для инвентаризации;
- инвентарь показывает реальные устройства и активные драйверы;
- граф не отображает синтетические связи как реальные;
- Driver Vault может импортировать, проверить и хранить оригинальный пакет;
- установка/обновление доступны только через подтверждённый и журналируемый сценарий;
- до изменения создаётся baseline, а сбой не маскируется под успех;
- есть Dashboard, Hardware Graph, Driver Vault, Time Duck и Audit;
- CI собирает и проверяет проект воспроизводимым способом;
- все неподдерживаемые операции явно обозначены.

Функции UDB, продвинутый DPC/ISR анализ, DuckMesh и kernel bridge не блокируют выпуск MVP.

## 14. Важные архитектурные уточнения исходной концепции

1. «Изоляция драйверов» в первой версии означает управление конфигурациями, проверку и тестирование пакетов в отдельном окружении (например, VM), а не универсальную виртуализацию произвольного kernel-mode драйвера.
2. «Hot-Swap» означает переключение только тех параметров, для которых ОС/устройство предоставляет безопасный механизм. Для остальных операций требуется остановка устройства или перезагрузка.
3. «Clean-Extract» анализирует и выбирает компоненты, но не изменяет оригинальные подписанные драйверные файлы.
4. «Нулевая дополнительная задержка» UDB Audio — исследовательская цель, не обещание. Любая маршрутизация измеряется на конкретном endpoint и конфигурации.
5. «Утиный индекс» рассчитывается по открытым показателям и всегда объясняет оценку.
6. «Автоматический откат» возможен только для состояния, которое DDC сохранил и умеет восстановить; ОС может потребовать reboot.
7. ddc_bridge — отдельное решение после прототипа user-mode API, аудита безопасности и тестирования.
8. Указанные в исходнике 18 MB RAM, 0.0% CPU, 120–240 FPS, 0.8 секунды snapshot и 1.5–3 секунды переключения профиля — измеряемые гипотезы, не acceptance criteria до появления воспроизводимого стенда.
